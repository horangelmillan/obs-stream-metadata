# ADR-011 — Integración YouTube OAuth vía backend (T-045)

- **Fecha:** 2026-09-09 · **Tarea:** T-045 · **Estado:** decidido, implementado y verificado en vivo.
- **Contexto:** ADR-009/T-038 (backend para YouTube), T-043 (fundación), T-044 (auth/sesiones). T-035 refutó secretless; T-037 cerró distribución. Trazabilidad: `docs/ARCHITECTURE-BACKEND.md` §4.
- **Flujo elegido:** `POST /connect/youtube` (sesión T-044) crea transacción `{state, PKCE, installation, TTL 600 s}` y devuelve `{transaction_id, authorization_url}` (sin secret/verifier/tokens). Browser del sistema → consentimiento → `GET /connect/youtube/callback?code&state` (sin bearer; la transacción+state son la autorización) → validación state/expiración/binding → exchange con secret (solo backend) → custodia en `TokenStore` → identidad `channels?part=snippet&mine=true` → `Connection{Account(channelId, title)}` → transacción consumida (anti-replay). `GET /connect/youtube/status` y `POST /connect/youtube/disconnect` con sesión T-044.
- **Por qué:** el callback termina en el backend (el plugin jamás ve `code`/`verifier`); la transacción separa OAuth efímero de sesión; single-use + TTL + state impredecible mitigan replay/CSRF.
- **Google requirements:** cliente Desktop + PKCE S256 + loopback + `access_type=offline` + `prompt=consent`; scope único `youtube.force-ssl`; secret requerido en nuestra configuración (T-035). Loopback Desktop aceptó `http://127.0.0.1:9004/connect/youtube/callback` con path (Observado; contrasta con el match exacto de Kick, F-017). Verificación del scope para producción: requerida para app pública (tier exacto OPEN, ver FAQ de verificación).
- **Token custody:** `TokenStore` backend (dev: memoria; prod: cifrado en reposo). Refresh con single-flight por cuenta + margen 120 s; `invalid_grant` → `SESSION_EXPIRED` (re-conectar, sin loops). Disconnect: borrado local siempre + revoke remoto best-effort (F-030). Al plugin: solo `{provider, status, account{id, displayName}}`.
- **Errores Google → modelo:** `invalid_grant`→`provider_rejected`; `invalid_client`→`internal` (config nuestra); `access_denied`/`invalid_scope`→`authorization`; 429→`provider_rate_limited`; 5xx→`provider_unavailable`.
- **Testing:** 14 tests nuevos (adapter + flujo con fake transport: replay/state/expiración/binding/refresh concurrente/disconnect); live PASS 2026-09-09 (consentimiento real, exchange, identidad, disconnect+revoke); secret-scan limpio.
- **Producción pendiente:** proyecto Cloud de producción + consent/branding + redirect HTTPS + verificación + secret manager + DB cifrada + TLS. Nada de esto marcado PASS.
- **Consecuencias:** T-046 replica este patrón para Kick; T-048 cablea Connect/status al dock sin cambiar el contrato.
